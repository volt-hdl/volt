# Volt 0.1.3

Volt 0.1.3 fixes bugs of 0.1.2 that gave a wrong result without a
diagnostic, and one security bug:

- **security**: `volt build` wrote through a symbolic link (or, on
  Windows, a directory junction) in `build/`, so building a cloned
  repository could overwrite a file outside it
  ([#221](https://github.com/volt-hdl/volt/issues/221));
- **wrong widths**: a `Trit` counted as one bit in the type checker, a
  `match` expression was computed at a narrower width than the same `if`,
  and a width of 65536 passed one check and was cut by the next;
- **wrong `match` hardware**: in a statement `match`, an arm written
  after the wildcard won for its own values, and assignments in arms that
  are never selected still counted as drivers;
- **lost checks and constraints**: a domain field written twice, a clock
  port declared through a type alias, a reset passed through `sync()` or
  used as data, a struct `sync()` whose type is not written, and a
  `Delayed<T, N>` declaration on a `let`, `wire` or output were not
  checked as the language says, and some constraint files missed lines;
- **tests that passed without running**: `volt test` reported "ok" when
  the simulation stopped in the middle of a test, and a whole-struct
  comparison or a port width given through an alias masked values that do
  not fit.

Upgrading is recommended. Many of these fixes reject input that 0.1.2
accepted; in each such case the 0.1.2 output was wrong. Read
[Behavior changes](#behavior-changes) before upgrading. If you keep
`build/` as a link on purpose, read the [security item](#security) before
you build: 0.1.3 refuses to write through it.

## Behavior changes

Upgrading from 0.1.2: for each item below, the same input gives a
different result in 0.1.3. Each item says what 0.1.2 did, what 0.1.3
does, who is affected and what to do. Where 0.1.2 compiled a design and
0.1.3 reports an error, writes different SystemVerilog or constraints, or
fails a test, the 0.1.2 result went against the language specification
or hid a failure. No new diagnostic code, command-line option or JSON
field comes with this release.

### Security

- **Volt no longer writes through a link**
  ([#221](https://github.com/volt-hdl/volt/issues/221)). Every file Volt
  writes stays under the output root, and a symbolic link in the path
  below the root, or as the file itself, stops the write. 0.1.2 followed
  such a link: when a cloned repository carried `build/rtl/Top.sv` as a
  link to a file elsewhere, `volt build` overwrote that file, and when
  `build/` itself was a link, every output went where it pointed. A
  repository can carry such a link, because git keeps symbolic links.
  0.1.3 reports `error: cannot write 'build/rtl/Top.sv'`, with a
  `= reason:` line that names the link and a `= help:` line that says to
  remove it or to pick another directory with `--target-dir`; it exits
  with code 3 and writes no file. The output root is the working
  directory for `volt build`, `run`, `test` and `verify` (`build/` is
  checked), or the `--target-dir` you give; the project directory for
  `volt new`; the working directory for `volt init`, where a dangling link
  is refused too; and the directory of the VCD file for `volt run --vcd`.
  The root itself and the directories above it are not checked: a home
  directory that is a link, or a `--target-dir` that you give as a link,
  works as before. On Windows a directory junction counts as a link;
  reparse points that leave the write in place (OneDrive placeholders,
  compression, deduplication) do not. A Verilator build directory that
  holds a link is deleted and built again, and `volt verify` refuses to
  run when `build/formal` holds one. On paths without links, the files
  Volt writes are byte for byte the same as in 0.1.2.
  *Who is affected:* anyone who builds a repository they did not write,
  and anyone who keeps `build/` (or a file in it) as a link on purpose.
  *What to do:* nothing, unless the link is yours; then pass the real
  directory with `--target-dir`.

### Clock domains and resets

- **A field written twice in a `domain` is `E1003`**
  ([#420](https://github.com/volt-hdl/volt/issues/420)). 0.1.2 compiled
  `reset = none` followed by `reset = sync active_high` in one domain
  without a diagnostic, and the compiler's passes read different lines:
  the SystemVerilog and the reset checks took the later one and generated
  a reset synchronizer, while the constraint generator took the domain
  as having no reset, so the XDC file lacked the
  `set_property ASYNC_REG TRUE` line of that synchronizer. 0.1.3 reports
  `error[E1003]: field 'reset' is written twice in domain 'Sys'`, points
  at both lines, exits with code 1 and writes no file. The rule holds for
  every domain key (`clock`, `frequency`, `reset`, `reset_cycles`,
  `reset_sequence`, `trust_level`), also when the two values are the
  same. An unknown key (`W0020`) does not count.
  *Who is affected:* designs whose `domain` writes a key twice.
  *What to do:* keep the line you mean and delete the other.
- **A clock or reset port declared through a type alias is checked like
  one written as `clock` or `reset`**
  ([#234](https://github.com/volt-hdl/volt/issues/234)). With
  `type Clk = clock`, `type Rst = reset(async, active_low)` or a chain
  such as `type Clk = ClkBase`, 0.1.2 missed checks: an asynchronous reset
  shared by `in fast_clk : Clk @Fast` and `in slow_clk : Clk @Slow` got no
  `E3003`, and `volt build --emit=sdc` wrote no constraint file for the
  aliased clock, printed "no module with a clock port in the unit" and
  exited with 0. In 0.1.3 both spellings behave the same. A design that
  0.1.2 accepted can now get `E3003`, `W3009`, `W3010`, `W3011` or
  `E8503` (a test drives a clock port); `--emit=sdc` writes
  `create_clock` and the reset constraints, and `--emit=sva` writes the
  automatic FSM and `@mmio` contracts. Some designs that 0.1.2 rejected
  or warned about now compile: `E1003` in an `@mmio` module, `E5011` in a
  pipeline, `E0017` on `@timing`, `E5010` on `sync(x, clk)` under
  `@strict_timing`, and `W1001`, `E2003` and `E3010` on an aliased raw
  reset port. The machine suggestion of `E0019` now writes the name of
  the clock port instead of `on <clock>`. An alias declared after the
  pipeline or module that uses it is still missed by two early checks
  ([#415](https://github.com/volt-hdl/volt/issues/415)).
  *Who is affected:* designs that declare clock or reset ports through a
  type alias.
  *What to do:* fix the new errors as their help says; declare aliases
  before the modules that use them.
- **Two instances that synchronize the same raw reset on the same clock
  get `E3003` when that clock is an instance output**
  ([#371](https://github.com/volt-hdl/volt/issues/371)), such as the
  `p.clk_o` of a PLL. 0.1.2 applied this rule to the top module's own
  clock ports alone: the design compiled, and the flattened netlist had
  two independent synchronizer chains on one clock, so two groups of
  registers could leave reset in different cycles. The error names the
  clock (`p.clk_o`). The SystemVerilog of designs that compile does not
  change.
  *Who is affected:* designs that clock several submodules from a
  generated clock and give each one the raw reset.
  *What to do:* synchronize the reset once for that clock and share the
  result, as the help of `E3003` says.
- **A reset cannot pass through `sync()` or `sync3()`, and a submodule's
  reset port takes the name of a reset input of this module**
  ([#340](https://github.com/volt-hdl/volt/issues/340)). 0.1.2 compiled
  `let rst_s = sync(rst, clk)` with `Child { clk: clk, rst: rst_s }`, but
  the flip-flops of `sync()` are cleared by a reset derived from the same
  port, so an active-high reset never reached the child: an `extern`
  child saw no reset, and the registers of a Volt child counted without
  ever being reset. 0.1.3 reports `E2003` for `sync(rst, clk)` and
  `sync3(rst, clk)` (both polarities), for a reset bound to a reset port
  through a `let`, and for a reset chosen with `if` or `match`. The
  diagnostic carries a machine suggestion. The SystemVerilog of designs
  that still compile does not change.
  *Who is affected:* designs that synchronize a reset by hand and pass it
  to a submodule.
  *What to do:* leave the reset port out of the instance; Volt connects
  the child's reset to the reset this module synchronizes for that clock
  (the suggestion does this). An `extern` module cannot take the
  synchronized copy yet ([#93](https://github.com/volt-hdl/volt/issues/93)):
  bind the reset input itself (`rst: rst`) and synchronize its release
  inside the SystemVerilog module.
- **A reset cannot be read as data**
  ([#356](https://github.com/volt-hdl/volt/issues/356)): as the subject
  of a `match`, or as an operand of `==`, `!=`, `<`, `>`, `<=` or `>=`.
  0.1.2 compiled `let t = match rst { true => true, _ => false }` with
  `y = sync(t, clk)`, and `y` was 0 in every cycle, because the reset
  cleared the synchronizer that sampled it; `rst == rst` and comparisons
  of two reset ports were accepted too. 0.1.3 reports `E2003` ("a reset
  cannot be used as a value of type 'bool'"), the same code and text that
  `if rst`, `!rst` and `let b : bool = rst` now get. `rst as bool` stays
  `E2009`.
  *Who is affected:* designs that read a reset as a value.
  *What to do:* for behavior at reset, use the reset value of a
  register; for a soft reset that software triggers, use a separate
  `bool` input port.
- **The constraints of a struct `sync()` are written per field when the
  source's type is not written**
  ([#373](https://github.com/volt-hdl/volt/issues/373)). When the source
  of `sync()` was an untyped `let` or `reg` holding a struct (a struct
  literal, another struct signal or constant, an `if` or `match`, a
  struct output of an instance, the `rd_data` of a FIFO of structs), 0.1.2
  generated one synchronizer per field in the SystemVerilog
  (`sync_p_a_stage0`, `sync_p_b_stage0`), but the `.sdc` and `.xdc` lines
  named a cell `sync_p_stage0_reg*` that does not exist: the false path
  (or `set_max_delay`) and `ASYNC_REG` matched nothing, without a word.
  0.1.3 writes them per field. The SystemVerilog does not change.
  *Who is affected:* designs that `sync()` such a struct value.
  *What to do:* build again and use the new constraint files.

### Types and widths

- **A `Trit` is two bits everywhere**
  ([#419](https://github.com/volt-hdl/volt/issues/419)). The type checker
  counted a `Trit` as one bit. With `ShiftRegister<Trit, 4>`, 0.1.2 typed
  `taps` as `bits<4>`: assigning it to a `bits<4>` port passed
  `volt check`, and `volt build` wrote `assign window = 4'(sr_taps);`,
  dropping two of the four stages, while the correct `bits<8>` port got
  `E2001`. In 0.1.3 `taps` of `ShiftRegister<T, N>` is `bits<2N>` for a
  `Trit`, the `bits<4>` port gets `E2001`, and `bits<8>` compiles. Other
  results of the same fix:
  `sync()` of a value wider than one bit gets `W3003` ("two-flop
  synchronization does not guarantee bit coherence"), now also for a
  `Trit` and for an array such as `[bool; 4]`; a `taps` wider than 65535
  bits is `E2025` (0.1.2 cut the product to 16 bits and took the 128000
  bits of `ShiftRegister<bits<2000>, 64>` as `bits<62464>`); the
  suggestion of `E2009` for a RAM of `Trit` says `Ram<u2, ...>`; and a
  `[bool; 1]` is one bit, so `E3001` on it carries the machine suggestion
  `sync(a, clk)` that a `bool` gets.
  *Who is affected:* designs that put a `Trit` in a shift register, an
  array or a `sync()`.
  *What to do:* declare the port as `bits<2N>`; for a value that must
  cross clock domains as a whole, follow the help of `W3003`. A build
  that treats warnings as errors may now fail.
- **The widest type is 65535 bits**
  ([#418](https://github.com/volt-hdl/volt/issues/418)). 0.1.2 accepted
  `bits<65536>` in one check and turned it into an error type without a
  diagnostic in the next: with `in x : bits<65536>`, `out y : bits<8>` and
  `y = x`, `volt check` reported nothing and `volt build` wrote
  `assign y = 8'(x);`, dropping 65528 bits. 0.1.3 reports
  `error[E2025]: invalid width: 65536` ("width must be in the range
  1..=65535") for `bits`, `uint` and `sint`, for a constant expression
  that reaches 65536, for a generic argument, and for type alias targets,
  `let`s inside blocks and function signatures; `bits<0>` in those places
  gets `E2025` instead of a misleading `E2005`.
  *Who is affected:* designs with a width above 65535.
  *What to do:* split the value into narrower parts.
- **A `match` expression has the width of the same `if` expression**
  ([#215](https://github.com/volt-hdl/volt/issues/215)). With `u8`
  operands, `let m = match c { true => a + b, _ => a - b }` was an 8-bit
  signal in the SystemVerilog of 0.1.2, so 200 + 100 gave 44; it is now 9
  bits and gives 300. The same bug cut the subject of a `match`
  (`match a + b { 44 => …, 300 => … }` took 300 for 44), a comparison
  operand (`(match …) == 44`) and an index (`p[(match …) +: 1]`). A
  `let` without a type whose arms are all literals
  (`let l = match c { true => 5, _ => 6 }`) is now `i32`, like the `if`
  form; 0.1.2 rejected it with `E2005`.
  *Who is affected:* designs with arithmetic in `match` arms or subjects.
  *What to do:* nothing; check results that relied on the cut value.
  `prev()` of such an expression is still cut
  ([#413](https://github.com/volt-hdl/volt/issues/413), under
  [Known issues](#known-issues)).
- **A chain of same-width casts keeps its value in a wider context, and
  Verilator accepts it** ([#303](https://github.com/volt-hdl/volt/issues/303)).
  `y = ((a | K1) & K2) as bits<43> as u43` with `y : u49` was
  `49'(((a | …) & …))` in 0.1.2 and is now `49'($unsigned(((a | …) & …)))`;
  `(s ^ (0x35 & t)) as i8 as i11` is now `11'($signed((…)))`. The values
  are the same (Icarus and Yosys agree on both forms), but Verilator
  stopped `volt test` and `volt run` on the old form with `WIDTHEXPAND`.
  The SystemVerilog changes for a compound expression followed by two
  such casts in a wider context; when the innermost operand is a name, a
  selection or a literal, it stays as it was.
  *Who is affected:* designs that Verilator rejected this way.
  *What to do:* nothing.
- **A signed `>>` by a constant amount of the width or more is written
  `>>> (w-1)`** ([#302](https://github.com/volt-hdl/volt/issues/302)). For
  `a >> 64` with `a : i63`, 0.1.2 wrote `a >>> 64`. IEEE gives both forms
  the same value (every bit is the sign bit), but Verilator 5.050 to
  5.052 gave 0 for a negative `a`, so `volt test` and `volt run` showed 0
  while synthesis, Yosys and `volt verify` showed -1. 0.1.3 gives -1
  everywhere. The text of `W2013` for a signed `>>` now says that the
  result is filled with the sign bit (0 or -1); its code is the same.
  Unsigned `>>`, `<<`, amounts below the width and amounts known at run
  time are written as before.
  *Who is affected:* designs with a signed `>>` that gets `W2013`.
  *What to do:* nothing; consider writing the intended constant instead.
- **A struct field width written with `if`, `match`, a bit operation or a
  chain of 33 to 64 constants compiles to SystemVerilog**
  ([#376](https://github.com/volt-hdl/volt/issues/376)). 0.1.2 accepted
  `a : uint<if WIDE { 4 } else { 8 }>` or `b : uint<6 & 3>` in the type
  checker and then stopped `volt build` with `E0003` ("not supported yet:
  struct type 'P' as a signal type"). 0.1.3 computes the struct layout
  with the evaluator that computes port widths. The SystemVerilog of
  designs that compiled before does not change.
  *Who is affected:* designs that got this `E0003`.
  *What to do:* nothing.

### `match`

- **In a statement `match`, arms after the wildcard are not written, and
  get `W2014`** ([#216](https://github.com/volt-hdl/volt/issues/216)).
  0.1.2 wrote these arms after `default:` in the `case`, and since
  SystemVerilog takes `default` when no other label matches, they won for
  their own values: `comb { match s { 0 => { y = 1 } _ => { y = 7 } 1 => { y = 9 } } }`
  gave 9 for `s = 1`. The language takes the earliest arm that matches,
  so 0.1.3 gives 7, as the expression form and a `const` `match` already
  did. `W2014` ("an earlier '_' arm already matches every value") now
  appears on every such arm in all three forms. A guarded arm after the
  wildcard gets `W2014` instead of `E0003`. A signal assigned in such an
  arm alone is no longer driven, and the automatic FSM contracts no longer
  cover a transition written there. `volt explain W2014` explains the
  wildcard case.
  *Who is affected:* statement `match`es with arms after `_`.
  *What to do:* if the arm should win for its values, move it above the
  wildcard; otherwise delete it.
- **An assignment in an arm after the wildcard is not a driver**
  ([#328](https://github.com/volt-hdl/volt/issues/328)). That arm is not
  part of the design, so its assignments are not in the hardware. An
  output assigned in such an arm alone now gets `E4002` ("output port 'c'
  is not driven"); bits of an output assigned there alone get `E4012`.
  0.1.2 compiled `comb { match s { 0 => { a = 1 } _ => { a = 7 } 1 => { a = 9; c = 3 } } }`
  and made `c` a latch. The other way round, an assignment there no
  longer conflicts with another driver of the same signal: 0.1.2 gave
  `E4001`, 0.1.3 gives `W2014` alone. The SystemVerilog does not change.
  *Who is affected:* designs that assign signals in arms after `_`.
  *What to do:* move the arm above the wildcard, or drive the signal in
  an arm that can be selected.
- **An assignment in an arm that earlier arms cover is not a driver**
  ([#331](https://github.com/volt-hdl/volt/issues/331)). In
  `0 => { a = 1 } 0 => { a = 9; c = 3 } _ => { a = 7 }` the second `0`
  arm is never selected: it is not written to the SystemVerilog and gets
  `W2014`, and so does an arm that names an enum variant a second time.
  An output assigned there alone gets `E4002`, its bits `E4012`; such an
  assignment no longer conflicts with another driver (`E4001`).
  *Who is affected:* designs with repeated `match` values.
  *What to do:* delete the repeated arm, or merge it into the earlier one.
- **An arm that is not written to the design reaches no hardware check**
  ([#332](https://github.com/volt-hdl/volt/issues/332)): an arm after the
  wildcard, or one that earlier arms cover, in a statement or an
  expression. The clock-domain checks (`E3001`, `E3011`, `E3012`), trust
  (`E3009`), `@strict_timing` (`E5010`), handshake (`E4007`), `@mmio`
  ownership (`E4006`), the SDC source clock of `sync()`, the automatic FSM
  contracts and the size limits of a nested `match` (`E0018`, `E2027`) no
  longer look at it. Code that 0.1.2 rejected can now compile:
  `comb { match s { _ => { slow = 1 } 1 => { slow = fast } } }` got
  `E3001` and now gets `W2014` alone. The arm is still type-checked.
  *Who is affected:* designs with such arms.
  *What to do:* nothing; read the `W2014` warnings.
- **Two `match` forms that Verilator rejected now give valid
  SystemVerilog** ([#331](https://github.com/volt-hdl/volt/issues/331),
  [#332](https://github.com/volt-hdl/volt/issues/332)). (1) A pattern that
  names an enum constant (`START => …` with `const START : S = S::B`)
  names that variant: a later arm `S::B => …` is not written, and in a
  `match` without `_` that names every variant the last arm becomes
  `default`. 0.1.2 took the pattern for a wildcard: the `case` had two
  `S_B` labels and no `default`, and Verilator stopped `volt test` with
  `CASEOVERLAP`, `CASEINCOMPLETE` and `LATCH`. Where the last arm of a
  `match` expression was already `default`, the change is a comment
  `// <Enum>_<Variant> (and invalid codes)`. (2) A write in an arm that
  is not written to the design no longer adds a reset assignment to the
  reset branch of its `on` block; 0.1.2 drove the register from two
  `always_ff` blocks, and Verilator stopped with `MULTIDRIVEN`. For valid
  input the values are the same.
  *Who is affected:* designs that Verilator rejected this way.
  *What to do:* nothing.
- **An enum constant whose value is not a variant name cannot be a
  `match` pattern** ([#331](https://github.com/volt-hdl/volt/issues/331),
  [#332](https://github.com/volt-hdl/volt/issues/332)).
  `const START : Mode = if c { Mode::Idle } else { Mode::Run }`, or a
  function call, used as a pattern now gets `E0003` ("not supported yet:
  enum constant 'START' as a pattern, whose variant the SystemVerilog
  emitter cannot resolve"). 0.1.2 compiled it. The checker resolves such
  a constant and the SystemVerilog emitter cannot, so the two would
  disagree on which arm is written, and with the driver fixes above a
  signal could be driven from two places without an error. A constant
  whose value is a variant (`const START : Mode = Mode::Idle`), or a
  chain of names ending in one, works as before.
  *Who is affected:* designs that use such a constant as a pattern; none
  of the repository's examples or the book does.
  *What to do:* write the variant, or a constant whose value is the
  variant.
- **A 256-arm `match` in an inner position no longer gets `E0018`**
  ([#336](https://github.com/volt-hdl/volt/issues/336)). The height of
  the chain a `match` becomes as an operand, condition, index, port
  binding or contract is its number of arms; `E0018` starts at 257.
  0.1.2 added one level for the arm bodies, so
  `y = (match s { 0 => 254, …, 254 => 0, _ => 255 }) ^ a` (255 arms and
  `_`) got `E0018`. A `match` nested in an arm or subject of another now
  reaches the limit when the arms on the path add up to more than 256 (a
  128-arm `match` inside an arm of a 128-arm `match` is valid). An
  operator in an arm body still adds a level. A `match` that is the whole
  right-hand side stays a `case` of any size; the SystemVerilog does not
  change.
  *Who is affected:* designs that got this `E0018`.
  *What to do:* nothing.

### Instances

- **Assigning to a port of a built-in primitive instance is `E4011`**
  ([#378](https://github.com/volt-hdl/volt/issues/378)): `cnt.overflow = true`,
  `f.rd_data = d`, or `cnt.overflow <= true` in an `on` block. 0.1.2
  accepted it and drove the same net from the primitive's `always_ff` and
  from an `assign`, which is not valid SystemVerilog: `volt build` exited
  with 0, Yosys made a netlist with two drivers, and Verilator stopped
  with `MULTIDRIVEN` (the `on` form got an `E0020` that called it a
  compiler bug). Writing to an input of a built-in got `E1009`; it is now
  `E4011` too. The rule already held for instances of user modules. The
  error says the port's direction.
  *Who is affected:* designs that assign to an instance's ports after
  the instance.
  *What to do:* read outputs, do not write them; bind inputs in the
  instance literal.

### Timing

- **A `Delayed<T, N>` declaration on a `let`, `wire` or output port is
  checked in `@strict_timing`**
  ([#354](https://github.com/volt-hdl/volt/issues/354)). When the delay
  of the value is known exactly, a declaration that does not match it is
  `E5010` ("declared delay does not match the value"). 0.1.2 checked the
  declaration on registers alone: `let s : Delayed<u32, 1> = b`, with `b`
  a register two cycles old, compiled, and `s + a` looked aligned while
  the simulation added values of two different cycles; the declaration of
  an output port (`out y : Delayed<u32, 5>`) was overridden by inference
  without a word. A declaration over a value that mixes stages is still
  taken as a claim and compiles
  ([#358](https://github.com/volt-hdl/volt/issues/358), planned for
  0.2.0). The SystemVerilog does not change; `volt explain E5010` gains a
  sentence.
  *Who is affected:* `@strict_timing` modules with such declarations.
  *What to do:* write the delay the value has, or add a stage register
  (the help of `E5010` shows one).

### `volt test` and simulation

- **A whole-struct comparison checks that each literal field fits**
  ([#375](https://github.com/volt-hdl/volt/issues/375)). In
  `assert_eq(dut.q, P { .. })` and `assert_ne`, 0.1.2 masked each field to
  its width: with `a : u4`, `P { a: 17, .. }` was compared as `a: 1`, and
  `assert_eq` passed on hardware that held 1. 0.1.3 applies the rule of
  whole-struct assignment: a constant field that does not fit gets
  `E8512`, and a computed field that does not fit fails the test with
  `port_overflow`. A negative value in range in a signed field stays
  valid.
  *Who is affected:* tests that compare structs with literals.
  *What to do:* write field values that fit their fields.
- **A test knows the width of a port or memory given through an alias or
  a constant expression** ([#376](https://github.com/volt-hdl/volt/issues/376)).
  With `type Nib = u4`, or `const W : u32 = 2 + 2` and `uint<W>`, the
  test language of 0.1.2 took the width as unknown: `dut.a = 31` and an
  `assert_ne(dut.q, 300)` that can never fail got no `E8512`; a computed
  31 reached the 4-bit port, Verilator did not mask it, the 4-bit output
  read 31, and `assert_eq(dut.q, 31)` passed. `load` into a
  `[uint<W>; N]` memory skipped the element width and length checks. In
  0.1.3 a constant value gets `E8512` or `E8510`, and a computed value
  fails the test with `port_overflow`. The generated SystemVerilog, SVA,
  SDC and XDC do not change.
  *Who is affected:* tests of modules whose port widths come from aliases
  or constants.
  *What to do:* correct the values the test writes or compares.
- **`volt test` reports a simulation that stops in the middle of a
  test** ([#377](https://github.com/volt-hdl/volt/issues/377)). 0.1.2 did
  not read the simulator's exit code: when `$fatal`, `$error`, `$stop` or
  a failing `assert` in an `extern` body stopped the test bench, that test
  and every later one vanished from the report, and the run printed
  "test result: ok" and exited with 0. In 0.1.3 the interrupted test is
  `FAILED`, with the exit code and the simulator's messages
  (`%Fatal: ...`) in its details; tests that never started are listed as
  `test <name> ... not run` and do not count as passed; the summary is
  `test result: FAILED. P passed; F failed; N not run`, and the run exits
  with code 5. `--nocapture` now also prints the simulator's standard
  error. The report and exit code of ordinary runs do not change. A
  `$finish` in an `extern` body is not covered
  ([#382](https://github.com/volt-hdl/volt/issues/382)).
  *Who is affected:* tests of designs with `extern` modules whose
  SystemVerilog can stop the simulation.
  *What to do:* fix the failing test; scripts that read the exit code
  get 5 where they got 0.
- **The recommended and pinned Verilator is 5.054**
  ([#309](https://github.com/volt-hdl/volt/issues/309)). When Verilator
  is not installed, `volt test` and `volt run` now run the
  `verilator/verilator:v5.054` image (pinned by digest): the next run
  downloads it once (about 250 MB), and the notice line says
  `(verilator/verilator:v5.054)`. `volt doctor` prints "Verilator 5.054,
  g++ 13.3". The reason: Verilator 5.050 to 5.052 gave 0 for a negative
  value in a signed `>>` whose amount is a port that an instance ties to a
  constant (`G { a: a, k: 64 }` with `y = a >> k`), where Volt cannot see
  the constant; 5.054 gives -1, as synthesis, Yosys and `volt verify` do.
  The generated SystemVerilog does not change. One narrower case of the
  same kind is still wrong in 5.054 (see [Known issues](#known-issues)).
  *Who is affected:* everyone who runs `volt test` or `volt run`.
  *What to do:* if `volt doctor` shows a local Verilator 5.050 to 5.052,
  update it to 5.054, or set `VOLT_TOOL_BACKEND=docker`.

### Register maps

- **`volt check-regmap` reports a redefined macro and a repeated
  register name** ([#374](https://github.com/volt-hdl/volt/issues/374)):
  `E9003`, exit code 1. For a file signed by another Volt version (whose
  accessor code is not compared), 0.1.2 reported "Match" and exited with
  0 when the C header redefined a macro or removed it with `#undef`, or
  when the register map named one register twice. The C preprocessor uses
  the definition in force where a macro is expanded, while 0.1.2 read the
  earliest one: with `#undef PWM_REGS_DUTY` followed by a new
  `#define PWM_REGS_DUTY (PWM_REGS_BASE + 0x14U)`, the header's accessors
  wrote to an address that 0.1.2 did not compare. 0.1.3 reads the last
  definition. A redefinition with the same text is valid C and is not a
  difference. Files that Volt generates give the same result.
  *Who is affected:* users who check edited headers or register maps.
  *What to do:* define each macro, register and field once.

### Diagnostic text

The diagnostic text of 2 codes was corrected: the help of `E2005` for a
width expression nested deeper than 64 levels now says so, and the help
and `volt explain` text of `E5010` now put a real stage register before
`delay<K>`, which adds no register and is a claim that Volt does not
check ([#376](https://github.com/volt-hdl/volt/issues/376),
[#232](https://github.com/volt-hdl/volt/issues/232)). Neither code
gained or lost a machine suggestion, and the input that triggers them is
the same.

## Known issues

These bugs are open. Each one is planned for a later release; where a
workaround exists, it is given. "Suspected" marks a bug found by reading
the code and not yet reproduced by running it.

### Wrong results without a diagnostic

- **`~` on a `Trit` gives a value outside the `Trit` set** (suspected,
  [#434](https://github.com/volt-hdl/volt/issues/434)): `~` works on the
  two-bit code, so `~t` for t = +1 reads as -2. Write `-t` to negate a
  `Trit`.
- **A `prev()` of a wide or signed expression compares at the wrong
  width** ([#413](https://github.com/volt-hdl/volt/issues/413)): with `u8`
  operands, `prev(a + b) != 300` compares the 8-bit sum. Keep the earlier
  value in a register of the right type yourself.
- **A `const` that does not fit its type**
  ([#214](https://github.com/volt-hdl/volt/issues/214)): with
  `const A : u8 = 255` and `const B : u8 = A + 1`, compile time sees 256
  and the hardware sees 0. Make every computed constant fit its type.
- **A `sync()` source clock lost in the constraints**
  ([#372](https://github.com/volt-hdl/volt/issues/372),
  [#421](https://github.com/volt-hdl/volt/issues/421)): when the source
  is an instance output, is reached through more than 8 `let`s, or is
  annotated with a clock port name (`@a_clk`) instead of a domain, the XDC
  writes `set_false_path` instead of `set_max_delay -datapath_only`
  (comment `# sync '…': ? -> …`), and with `@a_clk` a port source gets no
  capture register. Annotate with the domain name (`@A`), and check the
  `# sync` comments of the constraint files for a `?`.
- **A `create_clock` for the clock of a `clock = none` domain**
  (suspected, [#435](https://github.com/volt-hdl/volt/issues/435)). Check
  the SDC of designs with such a domain.
- **The clock outputs of an `extern module` have no domain**
  ([#208](https://github.com/volt-hdl/volt/issues/208)): nothing clocked
  by a PLL output is checked. Synchronize every value between these
  clocks by hand.
- **A register's reset value can be a signal and is not checked**
  ([#209](https://github.com/volt-hdl/volt/issues/209)). Use a constant
  reset value.
- **`E5010` is missed in a `comb` block**
  ([#217](https://github.com/volt-hdl/volt/issues/217)). Write such a
  choice as a `let`.
- **A timing constraint can apply to a second register**
  ([#219](https://github.com/volt-hdl/volt/issues/219)): `get_cells {slow_reg*}`
  also matches a register named `slow_reg`. Do not name a register
  `<name>_reg…` next to a constrained `<name>`.
- **`@false_path` and `@multicycle` are written without a check**
  ([#226](https://github.com/volt-hdl/volt/issues/226),
  [#231](https://github.com/volt-hdl/volt/issues/231)), and on a struct
  port they constrain nothing
  ([#229](https://github.com/volt-hdl/volt/issues/229)). Treat both as
  your own claim and check every path you mark.
- **Trust**: a secret passes through an unclassified input port of a
  submodule ([#210](https://github.com/volt-hdl/volt/issues/210)), and
  the trust annotation of a `wire` or `let` is not read
  ([#211](https://github.com/volt-hdl/volt/issues/211)). Annotate the
  ports.
- **Names**: a struct `let`'s flattened field can shadow a port
  ([#154](https://github.com/volt-hdl/volt/issues/154)); a module-level
  `let` can take the name of a bundle port or of `regs`
  ([#155](https://github.com/volt-hdl/volt/issues/155)); an import alias
  reaches the SystemVerilog
  ([#161](https://github.com/volt-hdl/volt/issues/161)); a test reads a
  private constant of another file
  ([#162](https://github.com/volt-hdl/volt/issues/162)); a port bound
  twice takes the last binding
  ([#229](https://github.com/volt-hdl/volt/issues/229)).
- **`@mmio`**: an unaligned base address and a repeated argument are
  accepted, and a `*/` in a `///` comment ends the C comment in the
  generated header ([#220](https://github.com/volt-hdl/volt/issues/220)).
- **A malformed `Volt.toml` is ignored**
  ([#222](https://github.com/volt-hdl/volt/issues/222)).
- **A `$finish` in an `extern` body lets the test continue**
  ([#382](https://github.com/volt-hdl/volt/issues/382)).
- **Arithmetic widths that change in 0.2.0**: an operand of `+`, `-` or
  `*` is cut before the operation, with `W2016`
  ([#266](https://github.com/volt-hdl/volt/issues/266)), and `/` or `%`
  can be computed at another width, with `W2015`
  ([#150](https://github.com/volt-hdl/volt/issues/150)). Put the
  intermediate result in a `let` of explicit width.
- **An incomplete assignment in a `comb` block infers a latch**
  ([#230](https://github.com/volt-hdl/volt/issues/230)). Assign every
  output on every path.
- **A signed shift of a wide sum can simulate wrong in Verilator 5.054**
  ([#311](https://github.com/volt-hdl/volt/issues/311), Verilator #9256):
  a signed value wider than 64 bits whose width is one more than a
  multiple of 32, computed by an expression and shifted by a port that an
  instance ties to a constant, gives `…0001` for a negative value.

### Errors, false warnings and failures

These do not give a wrong result: Volt stops with an error or warns where
nothing is wrong, or a step fails.

- **The one-line install failed on Ubuntu 26.04** in the project's tests,
  because of a dangling symbolic link
  ([#306](https://github.com/volt-hdl/volt/issues/306)). If it fails for
  you, use the [manual install](https://volthdl.org/tour/install.html#manual-install).
- **A false `E2003` for a reset port without a spec**
  ([#342](https://github.com/volt-hdl/volt/issues/342)): binding a reset
  port with a spec to a child's `in rst : reset` gets "expected 'reset',
  found 'reset'". Write the same spec on the child's port,
  `reset(sync, active_high)`.
- **A false `W3011`** ([#344](https://github.com/volt-hdl/volt/issues/344))
  in a module without registers that instantiates an `extern` and a Volt
  child with its own raw reset port; its label names a synchronizer that
  is not generated. The warning can be ignored there.
- **`delay<K>` inside a `fn` body has no effect** on the timing check,
  and nothing says so ([#362](https://github.com/volt-hdl/volt/issues/362)).
  Write `delay<K>` at the call site.
- **Constants written with `as`, `clog2` or `~`**
  ([#422](https://github.com/volt-hdl/volt/issues/422)): a constant written
  with `as` is checked with its uncut value (a false `W2013` for
  `x << (9 as u3)`, a false `E2006` for an index `const K : u32 = 5 as u2`),
  and a width constant that uses `clog2` or `~` stops `volt build` with an
  `E2005` that calls it not constant. Write the value itself.

## Install

Windows (PowerShell):

```powershell
irm https://volthdl.org/install.ps1 | iex
```

Linux and macOS:

```sh
curl -fsSL https://volthdl.org/install.sh | sh
```

Running the script again updates an installed Volt to this release.
`VOLT_VERSION=0.1.3` installs this release instead of the newest one. In
a new terminal, `volt --version` prints `volt 0.1.3` followed by the
commit in parentheses. The VS Code extension is attached to this release
as `volt-hdl-0.1.3.vsix`. Verifying a download, installing by hand and
the platform notes are unchanged from 0.1.0: see
[Install Volt](https://volthdl.org/tour/install.html).

## Support

The latest release is the supported one. Fixes go into `main` and ship
with the next release. Before 1.0, a new last digit (0.1.3) brings fixes
and a new middle digit (0.2.0) may break existing code; a fix for a
silent wrong result may reject input that was accepted before even in a
last-digit release, as in this one. Report bugs in the
[issues](https://github.com/volt-hdl/volt/issues).

The full change log, in Turkish:
[CHANGELOG.md](https://github.com/volt-hdl/volt/blob/v0.1.3/CHANGELOG.md).
Planned work: [Roadmap](https://github.com/volt-hdl/volt/blob/main/docs/roadmap.md).
